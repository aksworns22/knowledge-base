## 시스템 디자인을 배워야 하는 이유

[[시스템 디자인]]: 기능 요구사항과 비기능 요구사항을 만족하는 대규모 시스템을 만들기 위해 구성요소와 그 연결방식, API, 데이터 모델을 정하는 일이다.

시스템은 한 번에 완성되지 않는다. 

> 단순한 설계에서 시작해 성능을 재고, 병목을 찾아 고치기를 반복한다.

기능을 구현하는 것과 그 기능이 실제 트래픽과 장애 속에서 버티게 만드는 것은 꽤 다른 일이다.

## 설계 절차

실무에서 받는 요청은 모호하기에 모호한 요청에서 무엇을 만들 지 좁혀가야 한다.
- 쉽게 하는 실수는 문제를 이해하기보다 익숙한 해법을 끼워 맞추면서 엉뚱한 것을 그리는 것이다. (ex. 부하 2배라는 말을 듣자마자 서버를 늘리기)

실수를 줄이고 올바른 설계를 위해 다음 원칙을 따른다.

> 기능을 먼저 돌아가게 만들고, 품질 목표는 그 다음에 채운다.

## 저장소와 처리 구성요소를 파악하는 7가지 질문

1. 지금 데이터는 얼마나 큰가?
2. 시간이 지나면 어떤 속도로 늘어나는가?
3. 다른 시스템이나 사용자는 이 데이터를 어떻게 쓰는가?
4. 읽기가 많은가, 쓰기가 많은가?
5. 강한 일관성이 필요한가, 최종 일관성으로 충분한가?
6. 내구성 목표, 즉 데이터를 잃지 않아야 하는 정도는 얼마인가?
7. 저장하거나 전송할 때 지켜야 할 개인정보나 규제 요건이 있는가?

### 기능 요구사항 단계
| 분류      | 무엇인가                                                                               |
| ------- | ---------------------------------------------------------------------------------- |
| 기능 요구사항 | 시스템이 무엇을 하는가                                                                       |
| 비기능 제약  | 설계를 좌우하는 숫자. 하루 사용자 수(DAU), 초당 요청 수(QPS), 지연 목표(p99, 요청 100건 가운데 99건이 끝나는 시간) 같은 것 |
| 범위 밖    | 초점을 지키려고 일부러 뺀 것                                                                   |

### 비기능 요구사항

> 비기능 요구사항에는 꼭 숫자와 단위를 붙인다. '빠르게'나 '안정적으로'는 지켜졌는 지 확인할 방법 없다,.

기능 요구사항이 시스템이 무엇을 하는지라면, 비기능 요구사항은 그 일을 얼마나 잘 해내야 하는지다.
- 이러한 구분이 필요한 이유는 직원 100명이 쓰는 사내 영상 게시판에도 하루 수억 명이 보는 유튜브에도 영상 재생 기능은 똑같이 들어 있지만 구조는 비기능 요구사항 때문에 완전 다르다.
#### 가용성

[[가용성]]은 서비스가 멈추지 않고 요청에 응답하는 시간의 비율로 보통 99.9%처럼 퍼센트로 적는다.

퍼센트로 보면 99%와 99.9%는 별 차이가 없어보이지만 1년으로 바꾸면 각각 3.65일, 8.76시간이다. 그래서 가용성은 다운타임으로 바꿔 보고 정한다.

목표가 높아질수록 어렵고 자동 복구가 있어야 가능하다. 또 가용성은 기능마다 달라도 된다.

#### 확장성

[[확장성]]은 사용자와 데이터가 늘어도 같은 성능을 지킬 수 있는지다. 숫자로는 감당할 규모를 적는다. 
- 하루 활성 사용자 수(DAU)
- 가장 붐빌 때의 초당 요청 수 (피크 QPS)
- 하루에 쌓이는 데이터 양

#### 성능

성능은 사용자가 기다리는 시간이다. 시간을 적을 때는 평균 대신 p99를 쓴다. 
- 예를 들어 재생 요청 1,000건 가운데 980건은 0.5초, 20건은 8초가 걸렸다고 해 보자. 평균은 0.65초라 빨라 보이지만 p99는 8초다.

#### 신뢰성

[[신뢰성]]은 맡긴 것이 끝까지 무사한지다. 신뢰성은 잃어도 되는 양으로 적는다.
- ex. 업로드가 끝났다고 응답한 영상은 하나도 잃지 않는다

가용성 vs 신뢰성
- 1년 내내 잘 열리는 서비스라도 어제 올린 영상 일부가 깨져 있다면, 가용성은 높지만 신뢰성은 낮다.

#### 일관성은 어디까지 양보할까?

> 모든 항목을 최고 수준으로 요구하면 설계를 할 수 없다. 그래서 무엇을 양보해도 되는지도 함께 정한다.

[[일관성|최종 일관성]]은 잠깐 예전 값이 보여도 시간이 지나면 모든 복제본이 같아지는 것
#### [[CAP]]와 네트워크 끊김

네트워크 파티션: 서버는 모두 살아 있는데 서로 연락이 닿지 않는 상태
- 이 때 **요청이 오면 선택지는 예전 값을 주거나 오류를 돌려주는 것**이다.

| 글자                             | 뜻                            |
| ------------------------------ | ---------------------------- |
| C, 일관성(Consistency)            | 어느 복제본에서 읽어도 가장 최근에 쓴 값을 받는다 |
| A, 가용성(Availability)           | 살아 있는 서버라면 오류 대신 응답을 돌려준다    |
| P, 파티션 내성(Partition tolerance) | 네트워크가 끊겨도 시스템이 계속 동작한다       |

파티션 내성은 서버를 여러 개 나눈 이상 필수고.. 그럼 남은 질문은 하나!

> 파티션이 났을 때 일관성과 가용성 가운데 무엇을 지킬 것인가

- 주의할 점은 CAP의 A가 앞에서 정한 99.99% 같은 가용성 목표와 다르다는 것이다. CAP의 A는 파티션이 난 순간 살아 있는 서버가 오류 대신 답을 주는지를 묻는다.

#### PACELC : 평소 상황까지 다룬다!

파티션(P)이 나면 가용성(A)과 일관성(C) 가운데 하나를 고르고, 그렇지 않으면(Else) 지연(L)과 일관성(C) 가운데 하나를 고른다.

[[PACELC]]는 시스템 전체에 하나를 고르는 것이 아니라 데이터마다 다르게 고른다.

## Core Entities

시스템이 주고받거나 저장할 핵심 객체
- ex. 유튜브라면 영상, 사용자, 댓글 같은 것

| Core Entity | 이 시스템에서의 뜻                                                |
| ----------- | --------------------------------------------------------- |
| User        | 영상을 올리고, 보고, 반응하고, 댓글을 다는 사람                              |
| Video       | 업로드된 영상 하나. 제목, 설명, 올린 사람, 처리 상태(업로드됨, 인코딩 중, 시청 가능)를 갖는다 |
| VideoFile   | 영상 하나를 해상도와 코덱별로 인코딩한 결과물. 시청할 때 실제로 읽는 파일이다              |
| Thumbnail   | 영상 하나에 여러 장 붙는 미리보기 이미지                                   |
| Comment     | 영상에 단 댓글과 답글. 답글은 원래 댓글을 가리킨다                             |
| Reaction    | 사용자가 영상에 남긴 좋아요나 싫어요                                      |

### API

객체를 정했으면 이제 기능 요구사항을 하나씩 보며 필요한 호출과 입출력을 정한다.

기능 하나에서 API가 여럿 나올 수도 있고, 설계하다가 빠진 API가 보이면 여기로 돌아와 채우면 된다.

API 간 성격 차이는 다음 단계인 [[HLD]]에서 구성 요소를 고를 때 근거가 된다.

**[[멱등성]]**(idempotency): 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질
